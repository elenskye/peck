# Git Plan：版本和提交的规矩

这是站主对所有项目的开发规矩。项目自己的说明文件（`CLAUDE.md` / `AGENTS.md`）写得更具体的，以项目的为准。

## 开工前：先问这次是哪种程度

每次开发前先问站主这次属于哪一种（有提问工具就用提问工具），答了再动手。站主已经写明了版本号（「做 1.2.0」「【v1.0.4】」）就不用再问。

| 程度 | 版本号 | 例子 | 要不要分 Phase |
| --- | --- | --- | --- |
| 小幅优化、修 Bug | 升 z | `1.0.0 → 1.0.1` | 不分，直接做 |
| 新增功能、大幅优化 | 升 y，z 归零 | `1.0.0 → 1.1.0` | 先写 Phase 计划 |
| 大版本 | 升 x，y、z 归零 | `1.0.0 → 2.0.0` | 先写 Phase 计划 |

升不升大版本（x）只由站主定，不要自己提议升。

## 版本号

- 写法 `x.y.z`。先找出这个项目的版本号写在哪几处（`package.json`、`Cargo.toml` 和它的 lock、`tauri.conf.json`、`pyproject.toml`、`Info.plist` 这类），**几处一起改**，改完说一声改了哪几处。
- 项目的说明文件里写了版本号在哪就照它的；没写又找不到，问站主。

## Phase 计划（升 y、升 x 才要）

- 动代码前先把计划写下来给站主看：分成几个 Phase（比如 1.2.0 Phase 1–5），每个 Phase 写**做什么**和**怎么算做完**。写在项目的路线文档里（有 `docs/roadmap.md` 这类就用它，没有就问站主放哪）。
- 站主看过再做。只做计划里写的，不顺手扩。
- 一个 Phase 是一轮：做完、验过、提交，再做下一个。

## 提交

- 提交说明：`v<版本>: <description>`，版本是这一轮在做的那个版本，description 用小写英文、简约概括——`v1.0.1: fix some problems`、`v1.1.0: minor improvement` 这样就可以，不用写细。只写一行。
- **不署名**：不加 `Co-Authored-By`、「Generated with」这类行；用仓库配好的 `user.name` / `user.email`，不改 git 配置。
- 每一轮开发做完就提交。装了这个插件的项目里，一轮做完 Peck 会问你要一行提交说明、自己提交这一轮改过的文件——那一轮你就**不用再自己提交**。要在中途提交（比如一个 Phase 里分两笔），用 `git_commit` 工具，不要用命令行的 `git commit`。
- **push 由站主做**：不 push、不 force push、不改已经推过的历史、不开 PR；tag 站主说打才打。
- 每一轮结束告诉站主这一轮有哪几笔提交：短哈希、说明、一句话做了什么。

## 更新正式版（发版、安装、部署）

- 升 z 的：做完自动更新正式版。
- 升 y、升 x 的：只在最后一个 Phase 收尾时自动更新。中间站主可以自己更新，或者在某个 Phase 里要求你更新。
- 怎么更新每个项目不一样：照项目说明文件里写的步骤做；没写就问站主，不要猜。

## 一轮结束时对一下

1. 版本号几处一致，是这一轮该有的那个。
2. 该跑的检查跑过了（项目说明文件里写的），没验的如实说。
3. 改动提交了（或者 Peck 替你提交了），说明合格式、没有署名。
4. 没有 push。
5. 告诉站主这一轮的提交；升 y、升 x 的再说一句现在做到第几个 Phase、下一个是什么。
